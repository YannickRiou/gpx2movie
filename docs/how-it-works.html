01

What OpenFlyover does

You give OpenFlyover the track of an outing: a hike, a trail run, a bike ride, a ski tour. The app lays that track on a 3D model of the real terrain, covered with aerial photos. A virtual camera then flies along the track, like a drone following you. You can edit the film on a timeline (stops, titles, photos, videos, music), then save it as a video file. Everything happens on your own computer: your track is never uploaded anywhere.

  1. A track file

    A GPX or FIT file from a GPS watch, phone or bike computer: a list of positions, often with heights and times.

  2. 3D terrain

    Height data and aerial photos, downloaded as small square "tiles" from open services, become a 3D landscape.

  3. A camera flight

    The camera follows the track, slows down at summits and passes, and can stop, turn or rise for wide views.

  4. A film file

    The film is computed one image at a time and written as an MP4 or WebM video, a still image or a printable poster.

Two ways to use it

As a website you open in Chrome or Edge, served from any simple web host (or from your own computer). Or as a desktop application for Windows, macOS and Linux. Both run the same code.

Try it with the sample

The app ships with a sample track, public/samples/tour-du-mont-blanc-j1.gpx: the first stage of the Tour du Mont-Blanc, from Les Houches to Les Contamines. It is synthetic (generated by scripts/gen-sample-gpx.mjs), not a real recording. The button "Essayer avec l'exemple (Tour du Mont-Blanc)" loads it. This page uses it as its running example.

The interface is in French; this page quotes its labels in French, with a translation in brackets the first time.

02

Concepts in plain words

Each card explains one idea in a few sentences, then says where it shows up in OpenFlyover ("Here"). Paths such as src/terrain/ are folders of the project; the code map lists them all.

The web platform

Browser

A browser (Chrome, Edge, Firefox, Safari) downloads web pages and runs them on your computer. Modern browsers are complete application platforms: they can draw 3D graphics, encode video and save files. The part that does the work is called the browser engine.

Here: the whole application runs inside the browser. Chrome or Edge are recommended, because the video export relies on features that Firefox and Safari have not been tested with.

HTML, CSS and JavaScript

The three languages of a web page. HTML describes the structure (a heading, a button), CSS describes the look (colors, sizes, layout), and JavaScript is the programming language that makes the page react and compute.

Here: index.html is almost empty; JavaScript builds the whole interface. The styles are in src/ui/*.css, with the color palette in src/ui/theme.css.

TypeScript

JavaScript with labels that say what kind of data each value holds ("a number", "a list of track points"). A checker reads these labels before the program runs and reports mistakes. The labels are removed when the code is built, so the browser still runs plain JavaScript.

Here: every source file is .ts, or .tsx for files that also describe screen elements. Shared data shapes ("contracts") live in src/core/types.ts. npm run typecheck runs the checker in its strictest mode.

Node.js, npm and packages

Node.js runs JavaScript outside a browser, which is handy for development tools. npm installs "packages" (code written by others) listed in package.json into a node_modules/ folder.

Here: Node 24 is needed to develop, test and build, never to run the app: the finished website is a folder of plain files. Main packages: React, three.js, zustand, mediabunny and the Takram sky and cloud libraries.

React, components and state

React builds an interface out of components: small functions that turn data into a piece of screen (a button, a panel, a timeline). The data a component shows is its state. When the state changes, React redraws only what changed.

Here: React 19. The root component is src/App.tsx; panels and the timeline are in src/ui/; the 3D scene is also made of components, in src/scene/.

Store

A store is a shared box of state that any part of the program can read and change. Components that read it are redrawn when it changes. It avoids passing the same data by hand through dozens of components.

Here: stores use the zustand library. The main one, useAppStore in src/state/store.ts, holds the tracks, all the settings (including the edited film) and the playback position. Smaller stores hold the weather, the landmarks, the export progress, the media files and more.

Pure function

A function whose result depends only on what you give it, with no hidden memory and no side effects. Called twice with the same inputs, it returns the same answer. Such functions are easy to test and give reproducible results.

Here: the key design rule. The camera, the overlay, the film clock, the clouds and the water are pure functions of two numbers: the position along the track and the film time. That is why the exported film matches the preview (see the FAQ).

Drawing in 3D

GPU, WebGL and shaders

The GPU (graphics card) is a processor built to draw millions of triangles per second. WebGL is the browser's way of giving it work. Shaders are small programs that run on the GPU for every corner of a triangle and every pixel, to place and color them.

Here: the 3D view uses WebGL 2. A weak GPU makes the export slower; without any GPU, rendering falls back to SwiftShader, a slow software imitation used in automated tests.

three.js and react-three-fiber

three.js is a library that describes a 3D scene (shapes, materials, lights, a camera) and turns it into WebGL calls. react-three-fiber lets React components describe that scene, so the 3D view is built like the rest of the interface.

Here: three.js r186 and fiber 9. The scene root is src/scene/FlyoverCanvas.tsx.

Mesh and texture

A mesh is a 3D surface made of triangles. A texture is an image painted onto it, like wallpaper on a wall.

Here: each piece of terrain is a grid of 65 × 65 points (64 squares per side, each cut into two triangles), wearing an aerial photo as its texture (src/terrain/mesh.ts, imagery.ts).

Frame and fps

A video is a series of still images (frames) shown quickly one after another. The frame rate, in frames per second (fps), says how many. A 60-second film at 30 fps is 1,800 frames.

Here: the export draws every frame of the film one by one, at 24, 30 or 60 fps. The on-screen preview only redraws when something changes, to save power (src/scene/renderOnDemand.ts).

Maps and tracks

Tiles and zoom levels

Online maps are cut into square images called tiles, 256 or 512 pixels wide. At zoom level 0 a single tile shows the whole Earth; each level splits every tile into four, so detail doubles. A tile is named by three numbers: zoom, column and row (z/x/y).

Here: the tile maths is in src/geo/mercator.ts; the list of tile servers is in src/terrain/sources.ts. Terrain goes up to zoom 17; photos up to zoom 16 to 20, depending on the source.

Elevation tiles and imagery tiles

Elevation tiles look like strange colored images, but each pixel's color encodes a height. With the "Terrarium" encoding, height in meters = red × 256 + green + blue / 256 − 32,768. Imagery tiles are ordinary pictures: aerial photos (orthophotos, corrected to line up with the map), satellite images or topographic maps.

Here: heights come from Mapterhorn (default) or AWS Terrain Tiles and are decoded in src/terrain/dem.ts. Photos come from IGN in France, swisstopo in Switzerland, Esri or Sentinel-2 elsewhere.

GPX and FIT files

GPX is a text file (XML) listing points with latitude, longitude, and often height and time; almost every GPS app can export it. FIT is Garmin's compact binary format; it can also hold heart rate, cadence, power and temperature.

Here: src/import/gpx.ts reads GPX; src/import/fit.ts reads FIT with a small decoder of its own, written from the public FIT protocol description and downloaded only when the first FIT file is opened.

Coordinates and the local frame

A place on Earth is given by longitude (east–west) and latitude (north–south), in degrees. A 3D scene needs meters instead. Graphics cards compute with about seven significant digits, so coordinates measured from the center of the Earth (millions of meters) would lose centimeters.

Here: the scene uses a local frame in meters centered near the tracks: +X east, +Y up, +Z south. Conversions are done in full precision before anything reaches the GPU (src/geo/ellipsoid.ts).

Open data services and caches

Some websites answer questions from programs: "what was the weather here on that day?", "which summits are near this line?". A cache is a local copy of an answer, kept so the same question is not asked twice.

Here: weather from Open-Meteo, landmarks, lakes and paths from OpenStreetMap (Overpass), place names from Nominatim. None needs a key or an account; answers are cached in the browser.

Video

Codec and container

Raw frames are huge, so a codec compresses them (H.264, HEVC, VP9 or VP8 for images; AAC or Opus for sound). A container is the file format that stores the compressed streams side by side: MP4 or WebM.

Here: the app picks the first codec the computer accepts, in this order: H.264 in MP4, HEVC in MP4, VP9 in WebM, VP8 in WebM (src/export/encoder.ts).

WebCodecs, mediabunny and ffmpeg

WebCodecs is a browser feature that lets a page use the computer's video encoder. mediabunny is a library that writes the encoded frames and sound into a proper MP4 or WebM file. ffmpeg is a widely used command-line program that does the same outside the browser.

Here: WebCodecs plus mediabunny everywhere it exists. The Linux desktop app has no WebCodecs, so it sends frames to the system's ffmpeg instead (src-tauri/src/video.rs).

Building, shipping and checking

Bundler and build (Vite)

The source code is hundreds of files written for humans. A bundler turns them into a few optimized files the browser can load quickly; this step is the build. During development, the same tool serves the app and reloads it on every change.

Here: Vite 8. npm run dev serves the app at http://127.0.0.1:5173; npm run build writes the finished site to dist/ (about 16 MB, mostly sky and cloud textures). The first screen loads about 510 kB; the 3D engine and the rest arrive just after.

Static website

A static website is a folder of files that a web server sends as they are. All the logic runs in the visitor's browser. There is no application server and no database to install, secure or pay for.

Here: copy dist/ to any host that serves HTTPS. Each visitor's browser fetches tiles, weather and landmarks itself.

Desktop app (Tauri and Rust)

Tauri wraps a website in a native window that uses the system's own web engine (Edge WebView2 on Windows, WebKit on macOS, WebKitGTK on Linux). A small program written in Rust, a compiled language, adds what a web page cannot do alone, such as running ffmpeg.

Here: Tauri 2, in src-tauri/. It loads the same dist/ as the website.

Tests and end-to-end tests

Tests are small programs that check the code automatically. Unit tests call one module with known inputs and compare the answer. End-to-end (e2e) tests start the real app in a browser without a window and click through it like a user.

Here: Vitest runs 1,589 unit tests in 98 files, in a simulated browser called jsdom. npm run e2e drives the app in headless Chromium with puppeteer-core. cargo test checks the Rust code.

Linting

A linter reads the code without running it and flags risky or inconsistent patterns, a bit like a spelling and style checker for code.

Here: oxlint, through npm run lint. Zero errors are expected before a commit.

Continuous integration (CI)

CI is a service that runs the checks on a fresh machine every time code is pushed, so a mistake is caught even if someone forgot to run the tests.

Here: GitHub Actions. .github/workflows/ci.yml runs install, type check, lint, unit tests and build on every pull request and on master, and cargo test only when the desktop code (src-tauri/) changed. desktop.yml builds the installers on demand or on a version tag.

03

The big picture

The code is organized in layers. At the bottom, the program talks to the outside world: files on disk and open data services. In the middle, plain computing modules do the maths, without any screen code. Above them, stores hold the state. At the top, the React interface and the 3D scene read the stores and call the computing modules.

How the data flows

Reading left to right: a file is imported into the store; the scene and the overlay read the store and draw; the export asks the scene for one frame after another and writes them into a video. Underneath, three supporting flows: the project file saves and restores the store, map tiles feed the terrain, and weather and landmarks arrive from open services.

The rule that holds it together: preview = export

Two numbers describe any moment of the film: the progress (how far along the track the marker is, from 0 at the start to 1 at the end) and the film time (seconds since the first image). Everything that moves on screen (camera, overlay, labels, clouds, ripples on lakes, the sun, the self-drawing track) is computed from these two numbers only, never from the computer's clock. The preview calls those functions for each image it shows; the export calls the very same functions for each image it writes. So the film is exactly what you saw, and any single frame can be recomputed on its own.

The project document

A project is one self-contained JSON text file named <name>.openflyover.json. JSON is a simple text format for structured data. The file holds everything needed to rebuild the film on another computer, including the tracks themselves and the photos, videos and music used:

tour-du-mont-blanc-j1.openflyover.json
├─ format: "openflyover-project", version: 2
├─ name
├─ settings        every setting of the app: map sources, light, camera, pacing,
│                  the film (shots, stops, texts, media, music, points of interest),
│                  overlay, video format, poster, landmarks, ghost race…
├─ playback.speed
├─ tracks          the points of each track, stored column by column
└─ media           the photos, videos and music used by the film (embedded)

The code is in src/project/document.ts. When a file is opened, every setting is checked against the type of its default value; anything wrong falls back to the default with a message, so an older or damaged project still opens. The landmarks from OpenStreetMap are not saved: they are fetched again.

The platform layer: website or desktop

Opening a file, saving a file, writing a video to disk, remembering a preference and storing tiles all work differently in a browser and in the desktop app. The rest of the code never deals with that difference: it calls getPlatform() (src/platform/index.ts), which returns the right implementation.

04

One track, start to finish

Here is what happens, module by module, when you drop tour-du-mont-blanc-j1.gpx on the window and end up with an MP4 file. Each step names the file where the work is done.

  1. The drop is caught. The root component listens for files dropped anywhere on the window and asks the platform layer for them. A .gpx or .fit file is sent to the import, a .json file is opened as a project. src/App.tsx → getPlatform().droppedFiles → src/ui/projectActions.ts (openFiles, importTrackFiles)
  2. The file is read. The GPX text is parsed into segments of points (longitude, latitude, height, time, and sensor values when present), plus the named waypoints. For the sample: 351 points, with times starting on 12 July 2025. src/ui/importFlow.ts → src/import/index.ts (importFile) → src/import/gpx.ts (parseGpx)
  3. A track is built. Its distance, elevation gain and loss (heights smoothed, 3 m threshold against GPS noise), duration and bounding box are computed, and a color is chosen that stays readable on aerial photos. src/import/stats.ts (buildTrack) · src/import/index.ts (assignColors)
  4. The store takes it. The track joins the list. The store computes the box around all tracks and the origin of the local frame. Because the sample lies entirely in France, the imagery switches to IGN aerial photos (unless you already chose a source). A message announces the import. src/state/store.ts (addTracks, pickRegionalImagery) · src/ui/toast.ts
  5. The terrain loads. The scene creates a terrain engine over the track's box widened by 25 km. It downloads elevation and photo tiles, coarse ones first, then finer ones near the camera. The camera frames the whole track. src/scene/TerrainLayer.tsx → src/terrain/engine.ts · src/scene/CameraRig.tsx
  6. The track is draped. The red line is laid on the terrain at the height of the loaded tiles, and laid again each time finer tiles arrive. src/scene/TrackLines.tsx
  7. Weather and landmarks arrive. One request to Open-Meteo gets the hour-by-hour weather of that day along the track; one request to OpenStreetMap gets the summits, passes, huts and lakes around it. Both are cached. src/ui/WeatherPanel.tsx → src/weather/store.ts · src/ui/LandmarkPanel.tsx → src/osm/store.ts
  8. The film assembles itself. Climbs are detected from the recorded heights. A 4-second orbit stop is placed at each highlight (top of a climb, pass crossed, nearby summit), and passes, summits and huts on the way get a title card and a slow-down. The film has an opening shot, the flight and a closing shot. src/flyover/climbs.ts · src/film/assemble.ts · src/scene/usePacing.ts
  9. The film clock is built. It answers, for any film time, "which phase are we in (opening, flight, stop, closing), and where is the marker?". By default the flight lasts 60 seconds, stops included; the opening and closing shots add a few seconds. src/film/clock.ts (buildFilmClock, stateAt)
  10. You press play. On every screen refresh, the film time advances; the clock gives the progress; the camera function gives the camera position; the marker and the sun move; the overlay is drawn on top. src/scene/FlyoverRig.tsx → src/flyover/filmCamera.ts (computeFilmView) · src/overlay/OverlayCanvas.tsx → draw.ts
  11. You click "Exporter" (export). The export drawer opens. You click "Exporter la vidéo" (export the video); in Chrome, Edge and the desktop app a dialog asks where to save the file. The drawer places an export request in the export store. src/ui/ExportPanel.tsx → src/export/store.ts
  12. The frames are rendered. The export controller pauses playback and resizes the drawing area to the video size. It lists every frame of the film (with 1 s held at the start and 2 s at the end). For each frame it sets the progress and the film time, waits until the visible tiles are loaded (5 s at most), renders, and composes sky, 3D image and overlay on an off-screen canvas. src/export/ExportController.tsx · schedule.ts (buildFrameSchedule) · capture.ts (renderSettledFrame, composeFrame)
  13. The file is written. Each composed frame goes to the encoder; mediabunny writes the MP4 to disk as it goes, in 4 MiB pieces. Music and video sound are mixed beforehand and added as an AAC or Opus track. At the end, the view is restored and a message says where the file was saved. src/export/encoder.ts · src/export/nativeEncoder.ts · src/film/audio.ts (mixFilmAudio)
05

The main parts

Each card gives what the part does, the one idea to understand it, where its code lives, and how it is tested. Test files sit next to the code they check: camera.ts is tested by camera.test.ts in the same folder.

Terrain engine

src/terrain/ · src/scene/TerrainLayer.tsx
Does
Turns elevation and imagery tiles into the 3D ground, with more detail near the camera and less in the distance.
Key idea
A quadtree: each tile can be replaced by its four finer children. A tile splits when its triangles would look bigger than about 3 pixels on screen. The parent stays visible until all four children are ready, so the ground never shows holes. Tiles are downloaded 12 at a time; the last ~600 images are kept in memory; a failed download is retried three times. For each elevation tile, the matching photo tiles one zoom level deeper are stitched into a single texture. Only the tracks' box plus 25 km (at least 40 km across) is ever loaded.
Where
sources.ts (catalog of tile servers, the single source of truth), fetch.ts (downloads, cache, retries), dem.ts (heights from colors), imagery.ts (stitched texture), mesh.ts (tile geometry), quadtree.ts and engine.ts (choosing and loading tiles), heightField.ts (height under any point).
Tested
src/terrain/*.test.ts: the engine is tested with fake downloads injected in place of the network; src/scene/TerrainLayer.test.tsx.

Flyover camera and pacing

src/flyover/ · src/scene/FlyoverRig.tsx
Does
Decides where the camera is and where it looks at every instant, and how fast the marker moves along the track.
Key idea
The camera is a pure function of progress, film time, settings and terrain heights; it keeps no memory from one frame to the next. Five styles: chase, sway (helicopter-like swing in bends), orbit, top-down and cinematic; six named presets ("Poursuite", "Hélicoptère", "Drone haut", "Vue du dessus", "Orbite", "Cinéma"). The camera always stays at least 80 m above the ground with a clear view of the marker. Pacing, when turned on (it is off by default), also slows the flight near highlights. The flight lasts 60 s by default (15 s to 10 min), whatever the track length.
Where
path.ts (the track as a measurable path), camera.ts and cameraSettings.ts (flight camera), filmCamera.ts (opening and closing shots, stops, framings), pacing.ts, climbs.ts (climbs, categories 4 to HC), sun.ts, race.ts (ghost race), trackColor.ts (track colored by speed, slope…).
Tested
src/flyover/*.test.ts, including checks that the camera moves continuously as progress changes.

Film and timeline

src/film/ · src/ui/Timeline.tsx · src/ui/FilmInspector.tsx
Does
Holds the edited film and lets you change it like in video editing software: opening and closing shots, stops, titles and texts, photos and videos, music, speed sections, camera framings along the track, points of interest.
Key idea
"The track is the base": the continuous flight carries the film, and items on separate lanes are added to it. The film is assembled automatically when a track loads, then adjusted by hand. The opening and closing shots join the flight with a "Transition": "Enchaîné" (the camera glides into the flight), "Coupe" (a clean cut) or a fade to black or white; with a cut or a fade the wide view holds still until the boundary. The film clock converts film time into a phase and a progress. Every gesture on the timeline is computed by a pure function and recorded as one undo step. Music is analyzed to find its beats (60 to 180 beats per minute) so "Caler sur le rythme" (snap to the beat) can move titles, stops and slow-downs onto them.
Where
model.ts (what a film contains), assemble.ts (automatic stops and titles), clock.ts, timeline.ts (gestures, snapping), audio.ts and beats.ts (music), exif.ts, media.ts, video.ts (photos and videos), pois.ts; editing helpers in src/scene/usePacing.ts (editFilm).
Tested
src/film/*.test.ts: the clock is checked against the older pacing it replaced; beat detection is checked on click tracks at 90, 120 and 150 beats per minute, with noise and silence. The e2e scenario "timeline" adds a text and a stop.

Overlay ("Habillage")

src/overlay/ · src/ui/OverlayPanel.tsx
Does
Draws what sits on top of the 3D image: opening and closing cards, counters (distance, height, speed, heart rate…), elevation profile, mini-map, weather, logo, free text, timeline texts, photos and videos, ghost-race ranking and source credits.
Key idea
The overlay is not made of web page elements. One pure function, drawOverlay, paints it onto a 2D canvas. The preview calls it on a transparent canvas laid over the 3D view; the export calls it on each video frame. Sizes are in units of 1% of the shorter side of the image, so the layout is the same in 720p and 4K. Three styles ("Éditorial", "Diffusion", "Application"), whose colors and fonts can be changed for the whole overlay or per element. The overlay is off by default; the source credits are on.
Where
draw.ts, data.ts (values along the track), settings.ts, themes.ts, exportOverlay.ts (bridge to the export), OverlayCanvas.tsx (preview).
Tested
src/overlay/*.test.ts.

Labels, landmarks and points of interest

src/scene/Labels.tsx · src/osm/ · src/film/pois.ts
Does
Shows names floating over the terrain: tops of climbs, GPX waypoints, OpenStreetMap summits, passes, huts and lakes, kilometer markers, start and finish, your own points of interest ("Pique-nique", "Le chalet de Paul") and photos where they were taken.
Key idea
One OpenStreetMap request per track, for the box around it plus 3 km, cached for 30 days. The distance to the track is computed locally, so changing the types or the distance never sends a new request. Labels fade when the terrain hides them or when they are far away; when two overlap, the more important one wins. Their opacity depends only on the current view, so the export matches the preview.
Where
src/osm/overpass.ts (requests), landmarks.ts (filtering, priorities), store.ts; src/scene/Labels.tsx, labelModel.ts, labelSources.ts; panels src/ui/LandmarkPanel.tsx and PoiPanel.tsx.
Tested
src/osm/*.test.ts, src/scene/labelModel.test.ts, src/film/pois.test.ts.

Light, weather and atmosphere

src/scene/AtmosphereLayer.tsx · src/weather/ · src/flyover/sun.ts
Does
Gives the scene a physically based sky and haze, the sun at the real time of the outing, terrain shadows, a starry night, automatic exposure, the historical weather of the day, volumetric clouds, reflective lakes and rivers, and color grading ("Couleurs").
Key idea
The Takram libraries model how sunlight scatters in the air. The sun is placed at the time recorded under the marker, so a sunrise outing is lit like a sunrise. The weather comes from one Open-Meteo request per track (2 to 12 points along it) and drives haze, veiled sun and softer shadows. Clouds come from the recorded low, mid and high cloud cover and drift with the wind according to the film time. In the export, clouds are rendered several times per frame (2, 4 or 6) so a frame never depends on the previous one.
Where
src/scene/AtmosphereLayer.tsx, CloudsLayer.tsx, WaterLayer.tsx, weatherEffect.ts, terrainShadow.ts, exposure.ts, grading.ts; src/weather/openMeteo.ts, series.ts, sceneWeather.ts, sceneClouds.ts; src/osm/water.ts.
Tested
src/weather/*.test.ts, src/scene/exposure.test.ts, grading.test.ts, terrainShadow.test.ts, waterMesh.test.ts, src/flyover/sun.test.ts. The look itself is checked by eye (tests-gpu.md).

Export

src/export/ · src/poster/ · src/ui/ExportPanel.tsx
Does
Produces the film (MP4 or WebM in 16:9, 9:16, 1:1, 4:5 or 21:9, from 720p to 4K, at 24, 30 or 60 fps), a still image (PNG or JPEG), the overlay alone on a transparent background, several formats in one go, one film per track of a folder, and a printable poster (A4 or A3 at 300 dpi, or square).
Key idea
Because every frame is computed from progress and film time, the export simply walks through a list of frames. It never plays in real time: each frame waits for its terrain, so a slow computer gives the same film, only later. Where possible the file is written to disk while it is encoded (Chrome, Edge, desktop), otherwise it is kept in memory and downloaded at the end. The poster reuses the still-image path, then draws text and figures around the view.
Where
ExportController.tsx (runs a request), schedule.ts (frames, sizes), capture.ts (waiting, composing), encoder.ts (WebCodecs + mediabunny), nativeEncoder.ts (ffmpeg on Linux desktop), store.ts, batch.ts (several formats, one film per track), cliRender.ts; src/poster/.
Tested
src/export/*.test.ts and src/poster/*.test.ts (the encoder and the network are replaced by fakes); the e2e scenario "export" renders a real 320 × 180 video and a still image.

Project file, undo and presets

src/project/ · src/platform/projectLibrary.ts
Does
Saves and reopens everything as one file, undoes and redoes setting changes, keeps named presets, and keeps projects inside the app ("Mes projets", my projects).
Key idea
Settings are checked generically against the default settings, so a new setting needs no extra code to be saved and loaded. A format change raises the version (currently 2) and adds a migration. The undo history keeps only what changed; changes less than 400 ms apart count as one step, and so does a whole slider drag. A preset stores either all settings or one family: "Style de carte" (map style), "Trace, marqueur et étiquettes" (track, marker and labels), "Habillage" (overlay) or "Prise de vue (caméra, cadrage, lumière)" (shot: camera, framing, light). Presets never carry stops, texts or media, which belong to a track. "Mes projets" saves automatically 3 s after the last change.
Where
document.ts (file format, checks, migrations), apply.ts, history.ts, presets.ts; src/ui/ProjectPanel.tsx, src/ui/library.ts.
Tested
src/project/*.test.ts, src/ui/library.test.ts; the e2e scenario "projet" saves a project and reopens it in a fresh page.

Offline packs

src/offline/ · src/platform/tileCache.ts · src/ui/OfflinePanel.tsx
Does
"Préparer hors ligne" (prepare offline) downloads once all the tiles needed to fly over the loaded tracks, in a corridor 2, 5 or 10 km wide. The view and the export then work without a connection.
Key idea
The plan reproduces the terrain engine's own splitting rule, so the pack holds exactly what a flyover will ask for. A pack is identified by a fingerprint of its tile addresses: the same tracks with the same settings give the same pack, and running it again completes an unfinished one. Downloads go 4 at a time, with a daily limit per source that respects each provider's terms; above 150,000 tiles the pack is refused. The tile downloader always checks the packs before the network.
Where
plan.ts (which tiles), policy.ts (what each source allows), download.ts, packs.ts, store.ts; storage in src/platform/tileCache.ts.
Tested
src/offline/offline.test.ts.

Desktop app and command line

src-tauri/ · src/platform/desktop.ts · src/export/cliRender.ts
Does
Runs the same site in a native window for Windows, macOS and Linux, with system dialogs, direct file access, ffmpeg encoding on Linux, and batch rendering from a terminal: openflyover --rendu <tracks folder> --sortie <films folder> --prereglage <preset> --formats 16:9@1080p,9:16@1080p.
Key idea
Everything that differs goes through the platform layer. The Rust side is small and locked down: only listed commands can be called (eight of them: six for the ffmpeg encoder, two for the command line, plus the plugins for dialogs, files and the Strava sign-in), and the app can read and write only the files you chose, its own tiles/ and projects/ folders, and the two folders given on the command line. A security policy lists every server the app may contact. The command line writes a report, rendu-en-lot.txt, and exits with 0 (all films done), 1 (a film failed) or 2 (the command could not run). Closing the window first finishes the last write of "Mes projets" and asks before losing unsaved changes; a running ffmpeg is stopped.
Where
src-tauri/src/lib.rs (setup), video.rs (ffmpeg), cli.rs (arguments), src-tauri/tauri.conf.json (window, security policy), src-tauri/capabilities/default.json (permissions); src/platform/desktop.ts.
Tested
cargo test in src-tauri/ (9 tests: ffmpeg arguments and command-line parsing), src/platform/platform.test.ts, src/export/nativeEncoder.test.ts (with a fake Rust bridge), src/export/cliRender.test.ts. The app has not yet been launched or packaged on a real machine.

Also in the code

src/route/ · src/plan/ · src/strava/ · src/import/chain.ts · src/flyover/race.ts
Scouting
"Préparer une sortie" (plan an outing): type a place or coordinates, place waypoints with a right-click, and "Calculer l'itinéraire" (compute the route) links them along OpenStreetMap paths with a shortest-path search (A*) that prefers trails to roads. The result is a track without times, flown over like any other (src/route/, src/osm/paths.ts, src/osm/geocode.ts).
Planned outing
A track without times (a computed route, or one prepared on Komoot or Visorando) gets "Prévoir la sortie" (plan the outing): date, start time, activity and pace give estimated passing times, so the sun, the counters and the weather (Open-Meteo forecast instead of the archive) follow the planned day. The "Feuille de route" (roadbook) lists the steep sections, passes, summits, huts and water points with their km, elevation, D+ and passing time, to copy or save as text (src/plan/timing.ts, src/plan/roadbook.ts).
Strava import
"Importer depuis Strava" reads your activities through your own Strava application: you create it once on Strava and type its client ID and secret in the app, which keeps them in this browser or on this computer and sends them only to Strava. No key ships with the code and there is no server in between (src/strava/, src/ui/StravaImport.tsx, src/platform/oauthRedirect.ts).
Chaining
"Enchaîner en un seul parcours" merges several tracks (one per day, say) into one route; the jump between days is neither drawn nor counted (src/import/chain.ts).
Ghost race
Several tracks replayed together, synchronized by elapsed time, clock time or distance, with a live ranking (src/flyover/race.ts, src/scene/RaceMarkers.tsx).

  • Desktop installers: GitHub builds them for the three systems ("Desktop installers" workflow). For a release, set the same version in src-tauri/tauri.conf.json and src-tauri/Cargo.toml, then push a tag such as v0.2.0: a release with the installers is published once the three systems are built. Details and signing: docs/installers.md.

Conventions

  • Language: the interface is in French; documentation (README, ARCHITECTURE, docs/) is in English, quoting interface labels in French.
  • Strict TypeScript: types are imported with import type; no enum and no constructor parameter properties (the compiler options verbatimModuleSyntax and erasableSyntaxOnly enforce this).
  • No React in src/geo/, src/import/ and src/terrain/: they stay plain computing modules.
  • Files and storage always go through getPlatform(), never directly through the browser or Tauri.
  • Data sources: open and keyless only. A new source goes into src/terrain/sources.ts, docs/sources.md and the security policy in src-tauri/tauri.conf.json.
  • Two targets: the website and the desktop app must both keep working; no Node.js at run time.
  • Look: the "Carte alpine" palette in src/ui/theme.css, bundled fonts (Fraunces, IBM Plex), Lucide icons.
  • Before each commit: types, lint and tests green; one commit per feature. Each test file sits next to its module.

On the development machines, Node is not on the default path: under WSL, run source ~/.nvm/nvm.sh && nvm use 24 first; on Windows, see the path given in the README. The current state of the work is in docs/handover.md.

Known limits and open points

From docs/handover.md and ARCHITECTURE.md. The roadmap has nothing left to build; what remains is mostly checking on real hardware.

  • to checkNever seen on a real graphics card: export speed, smoothness, sound and the final look. Development uses software rendering. The checklist is docs/tests-gpu.md.
  • to checkThe desktop app has not been launched or packaged on a real machine, and the installer workflows have not run yet. Installers are not signed, so Windows and macOS warn on first launch.
  • licensesEsri terms to re-read for online use; EOX and Open-Meteo are non-commercial; the license of the star catalog (Yale Bright Star Catalog) is not stated.
  • browsersExport not tested in Firefox or Safari. Without direct writing to disk, the video is built in memory (about twice its size); the drawer warns above an estimated 1.5 GB. HTTPS is required outside localhost.
  • hostingThe website must be served at the root of a domain: a few paths (/samples/, /fonts/, /favicon.svg) are written in full.
  • Linux desktopVideo export needs the system ffmpeg; the transparent "overlay only" export is not available there.
  • mediaVideos up to 50 MB, embedded in the project file (about 1.33 times their size). HEIC photos are refused; photo dates and positions are read only from JPEG files. Videos are synced to the track by time only, not by GPS.
  • renderingShadows only from the loaded area; clouds do not shade the terrain; the weather of a single point applies to the whole scene; water reflects an average sky, not the mountains.
  • editingAfter chaining tracks, stops and framings placed on the old first track are not moved to the new one.
  • testsNo tests that render interface components; the e2e tests cover the main flows, but the look is still checked by eye with screenshots.
  • scoutingIts usefulness is in doubt: it is not to be extended (bike profiles were dropped), and may be removed.
10

Questions and answers

Why does the export match the preview?

Because both call the same functions with the same two numbers: the progress along the track and the film time. The camera (computeFilmView), the overlay (drawOverlay), the labels, the clouds, the water and the sun depend on nothing else: not on the computer's clock, not on what was drawn the frame before. The only difference is patience: the export waits for the terrain of each frame to load before drawing it.

Why is there no server?

A server costs money, must be kept secure, and would see your tracks. Browsers can now do everything needed locally: 3D drawing (WebGL), video encoding (WebCodecs) and file saving. So the site is only a folder of files; each visitor's browser does the work and fetches open data directly from its providers.

What happens offline?

The app itself still runs, and so does anything already loaded. New terrain and photos cannot be downloaded: tiles that fail leave the coarser level visible, and the export waits for them as it would online. To work offline on purpose, prepare an offline pack first ("Hors ligne" section of the "Trace" tab): the tiles of a corridor around the track are stored on your computer and read before the network. Weather and landmarks already fetched stay in the cache.

Where are my projects stored?

"Enregistrer" (save, Ctrl+S) writes a <name>.openflyover.json file wherever you choose (or into your downloads folder). It contains everything, tracks and media included.

"Garder dans Mes projets" (keep in my projects) keeps a copy inside the app, saved automatically: on the website in the browser's Cache Storage (cache openflyover-projects-v1), on the desktop in the projects/ folder of the app's data folder. Presets, interface preferences and the weather cache are kept in the browser's local storage (inside the app folder on the desktop).

Is my track sent anywhere?

No. Tile servers only see which map squares are requested. The weather service receives a few points rounded to 1 km with their dates, and OpenStreetMap receives the box around the track. Weather and landmark requests can be turned off in the panels; then nothing is sent.

Why Chrome or Edge?

They have WebCodecs, used to encode the video, and they can write the file to disk while it is being made. Firefox and Safari have not been tested for export; without writing to disk, a long film has to fit in memory.

Why does an export take longer than the film?

Each frame is drawn at full size, waits until the visible terrain is loaded, and, with clouds on, is drawn several times to be clean. The speed depends mostly on the graphics card. The film is the same however long it takes.

How would I add a new map source?

Check that it is open and needs no key. Add it to src/terrain/sources.ts, document the checks in docs/sources.md, add its server to the security policy in src-tauri/tauri.conf.json (otherwise the desktop app blocks it), and decide whether it may go into offline packs in src/offline/policy.ts (a source missing from that table stays online only).

What is the difference between a .ts and a .tsx file?

Both are TypeScript. A .tsx file may also contain JSX, a notation that looks like HTML and is used by React components to describe what they show. Computing modules are .ts; interface and scene components are .tsx.
